## Relationship to prior plans

Builds directly on:
- **GR-PLAN-004** — Shopify product/SKU data model (`shopify_products` table), the GR SKU scheme, the OAuth Client Credentials Grant connection to the Shopify Admin API, and the reconciliation UX pattern (auto-suggested candidates, manual fallback dropdown, persist-per-item).

This plan reverses GR-PLAN-004's explicit v1 exclusions ("no inbound order reading," "no print-queue automation"). ## James's workflow, as described (ground truth for this design)

1. Order received for N items, each linked by SKU.
2. He browses for the product by name.
3. Opens it in Bambu Studio and prints.
4. *(new)* Marks the order as printed.
5. *(separate, later)* Generates shipping separately, adds the shipping info to the order, marks it fulfilled.

## Feasibility verdict

Yes — everything here is buildable on top of what already exists in Printventory. One real constraint: James asked for sync "ideally automatically with an event," with schedule as an accepted fallback. True event-driven sync (a Shopify webhook) needs a publicly reachable HTTPS endpoint; Printventory is a local Electron desktop app with no stable public address, so a genuine webhook listener isn't practical without extra always-on infrastructure. Scheduled polling plus a manual "Sync now" button is the practical default — see "Sync mechanism" below.

## Decisions locked in (2026-10-05)

### Print sequencing: FIFO with manual reordering, not an automated optimizer

GR-PLAN-005 raised a real scheduling insight (don't let a long overnight print block a short one that could finish and be handled sooner). Decided **not** to build an automated duration-based optimizer in this phase:

- There is no print-duration data in Printventory today (confirmed above) — no estimate, no history. An optimizer would have nothing real to optimize against, and a duration is only actually known once a file is opened and sliced in Bambu Studio — which is already the step *after* the order is picked.
- James knows things a scheduler can't (rush orders, filament already loaded, printer quirks) — a freely-reorderable queue keeps that judgment with him rather than fighting an automated ordering that's occasionally wrong.
- **Going forward:** the order queue defaults to FIFO (oldest order first; the Orders pane list is already rendered in this order) and is intended to become fully manually reorderable (drag or up/down — not yet built, see Phase A remaining work below). As a low-cost byproduct, "Mark Printed" should optionally support logging an actual elapsed duration into `print_events`, so real historical duration-per-model data starts accumulating. Once there's enough of that, the GR-PLAN-005 optimizer becomes a real, data-grounded Phase C project instead of a guess.

### UX pattern: pane + persistent badge + transient toast — not a persistent banner

- **New dockable "Orders" pane — built 2026-10-05**, same pattern as the existing Filters/Tools panes, with its own edge tab (📦 Orders) that can be pinned, auto-hidden, resized, or closed the same way.
- **Persistent badge on the edge tab — built 2026-10-05**, showing the count of open orders, with a distinct color (orange vs. green) when any line still needs manual linking. This is the ambient, always-available "is there anything to do" signal — appropriate because having some orders in flight is the normal state, not an exceptional one.
- **Transient auto-dismissing toast — built 2026-10-05** (~4s, no click required), shown only when a completed sync brings in new orders ("3 new orders synced"). Kept separate from the badge so neither has to do both jobs. Fires from both the manual "Sync now" button and the background interval sync, via a new `shopify-orders-synced` IPC event (see Sync mechanism below).
- **Explicitly not** a persistent alert banner for "orders pending" — that duplicates the badge's job and risks banner-blindness/dismiss-fatigue for something that's a constant, normal state rather than an exception.
- **Settled (2026-10-05):** the badge is one combined number (open-order count), with a color change (not a second number) flagging unmatched lines — simpler than a split two-number signal, and the backend (`get-shopify-orders-badge-count`) already tracks both counts separately if a split display is wanted later.

### Bundle and unmatched-SKU handling: variant-aware match, reusing the existing product editor — 2026-10-05, refined after testing

James's original question: what happens when a line's SKU hasn't been synced/matched, or the order is for a multi-variant bundle (his example: Halloween Ghosts has 8 individual-ghost SKUs plus a 9th "complete set" SKU covering all 8)? A single "Open in Slicer" button can't honestly resolve a bundle SKU to one file.

Decided against an external "View in Shopify" admin-page link (the first draft shown in the wireframes) — James redirected this: reuse Printventory's **own** existing product management UI instead of sending him out to Shopify's website. Investigation found `populateVariantAssignments()` (renderer.js) already does exactly this job: the product editor dialog lists every variant on a product, each with its own thumbnail, suggested file, and "Open" button — no new feature needed, just route to it.

**First pass** (commit `5eb6cf2`) matched three ways: SKU → `shopify_variants` ("auto-matched", open directly) → parent product gid → `shopify_products` ("product-linked", open product manager) → "unmatched". This shipped a real bug, caught immediately in James's testing: a line for a "Complete Set of 9" bundle SKU (`GR-LAD-SET`) *did* resolve via `shopify_variants` (the set SKU had its own variant row), so it was treated as "auto-matched" and showed "Open in Slicer" pointing at one arbitrary file ("Dead Romantic.3mf") instead of routing to the product manager. The flaw: a SKU resolving via `shopify_variants` only proves the *product* is linked, not that `shopify_products.model_id` (its primary/representative model) is the *correct* file for every variant's SKU on a multi-variant product.

**Fixed same day** (commit `df4e420`) — `matchOrderLineItem()` (main.js) is now checked in order, most specific first:

1. **A confirmed per-variant file assignment** — originally `shopify_product_files.shopify_variant_id` (keyed on the Shopify variant's own gid), now `shopify_variant_file_links` (see the multi-variant-per-file fix below) — resolves to a specific model. This is exactly what the product editor's variant picker (`populateVariantAssignments()`) writes when James links one variant to one file in there. When present, it's trusted regardless of anything else about the product — **`auto-matched`**, opens directly.
2. **A bare SKU match via `shopify_variants`**, but only trusted as safe-to-open-directly when the matched product has a **single variant** (no ambiguity possible). A multi-variant product's SKU match still resolves `matched_model_id` (for display/record purposes) but the *action* falls to **`product-linked`** instead, regardless of whether its own SKU "matched" — because without a per-variant assignment (#1), there's no way to know the representative model is the right one for this specific line.
3. **Parent product gid fallback** (unchanged from the first pass) — the line's own SKU was never imported as a variant at all, but the parent product is linked. **`product-linked`**.
4. **`unmatched`** — neither resolves. Manual-link combobox (see below).
5. **`manually-linked`** — unchanged, protected from being overwritten by a re-sync (same protection now also covers `product-linked`).

Action mapping, unchanged from the first pass: `auto-matched`/`manually-linked` → **Open in Slicer**, direct. `product-linked` → **Open Product Manager** (`window.openShopifyProductEditorForPath()` on the product's primary model file), **enabled only if a model file actually resolves** — **disabled otherwise**, per James's explicit clarification ("if its linked" / "it can be disabled otherwise"), rather than hidden or erroring.

`shopify_order_line_items` gained a `shopify_variant_gid` column (migrated) to carry the Shopify variant's own gid through to the matcher, alongside the `variant_title`/`unit_price`/`unit_price_currency`/`shopify_image_url`/`shopify_product_gid` columns added in the first pass (needed for the Option A card's variant tag / price / thumbnail, and for the parent-product fallback).

**Third-round refinement (commit `8783c8a`):** inside the product editor dialog itself, a suggested-but-unconfirmed variant row only showed Confirm/Other buttons — no way to preview the suggested file before confirming it, unlike an already-assigned row which has an Open button. James: "the button to open the model is hidden. Would it be better to add it again to the variants list and resize the boxes?" Added an Open button to the suggested branch too (reusing the existing `.open-file-btn` class and its already-delegated click handler — no new wiring needed), pointed at the suggested file's path, and loosened `.variant-info`/`.variant-file-assignment` widths slightly so three buttons (Confirm/Other/Open) have room instead of crowding the filename/match-score.

**Round 4 — the Open button fix above landed in the wrong (though related) place:** James's round-3 screenshots actually showed two different UI elements, and the fix only reached one of them. `8783c8a` added the Open button to the collapsible "Variant Assignments" dialog (`populateVariantAssignments()` / `#shopify-variant-list`), which the user has to expand via a `<details>` summary. James was pointing at the separate, always-visible "Variants (N)" table (`renderShopifyVariantsTable()` / `#shopify-variants-table`) directly below it in the product editor — a plain SKU/Price/Stock grid built straight from raw Shopify variant data, with no file information at all. Fixed in commit `a5e2563`: added a second pass, `renderVariantsTableFileButtons()`, that runs after `populateVariantAssignments()` has fetched assignment/suggestion data (`window._shopifyEditorContext.variantData`) and fills in a new File column per row — an Open button for an assigned or suggested-but-unconfirmed file (title text notes when it's only a suggestion), or a muted dash when neither exists. Needed its own click delegation (`bindVariantsTableFileButtons()`) since this table sits outside `#shopify-variant-list`, the only container the existing delegated handler reaches. `styles.css` gained a 5th grid column for it.

James also separately confirmed (round 4) that seeing every multi-variant order line in his round-3 screenshot route to "Open Product Manager" — rather than some opening a file directly — was the correct, intended behavior per the matching rule above (a SKU only auto-opens directly when its own variant has a confirmed per-file assignment, or the product has just one variant). No change needed there; as per-variant assignments get confirmed in the product editor, those lines will start auto-matching and show "Open in Slicer" directly on the next sync.

### Variant-to-file assignment: one file can now back several variants — 2026-10-05

Checking why a batch of multi-variant lines (The Dark Guardian, The Velvet Gaze, The Sly Regent) were all routing to "Open Product Manager" surfaced this real question from James: **Gremlin Relics hand-paints several finish variants from the same physical print** — "Matte Black" / "Bronze & Silver" / "Other (message me)" on The Dark Guardian are one sculpt, one `.3mf`, painted differently after printing. Confirming "Matte Black" against that file in the product editor worked fine; trying to confirm "Bronze & Silver" against the *same* file silently wiped Matte Black's assignment instead of adding a second one — "I can't link to multiple variants."

Root cause, confirmed in code: `shopify_product_files` (the table the variant picker was writing to) had `UNIQUE(folder_path, model_id)` — one row per file, so a file could only ever carry one variant's gid at a time. Assigning a second variant to the same file didn't add a mapping, it overwrote the only row that file had.

Fixed (commit `c0acd4b`) by adding a new table, `shopify_variant_file_links`, keyed the other way around — `UNIQUE(folder_path, shopify_variant_id)`. A variant still always resolves to exactly one file (reassigning it replaces the row, same guarantee as before), but nothing stops several variants pointing at the same `model_id`. `shopify_product_files` keeps its original, narrower job (is_primary/link_status per file) but no longer decides variant assignment. `assignFileVariantHandler`, `getProductVariantsWithSuggestionsHandler`, and `matchOrderLineItem`'s confirmed-assignment lookup all now read/write the new table; a one-time backfill (guarded on the new table being empty, so it only ever runs once) copies across any assignments already confirmed under the old scheme (e.g. `GR-LAD-SET`'s) so nothing already done was lost.

Per James's "I don't mind being given a warning if linking multiple" — the manual file picker (`showFilePickerForVariant` in renderer.js) now shows "Also used for: X, Y" as an informational note (not a block) next to a file already backing other variants, replacing the old singular "Assigned to" label that implied exclusivity. Suggestions also no longer exclude already-assigned files from being suggested again — reuse across finish variants is now an expected case, not a mistake to guard against (a suggestion still always needs explicit confirmation either way, so this doesn't risk silently reassigning anything).

**Round 5 — the transient note wasn't enough, commit `c8d866a`:** James confirmed the core fix worked (screenshot: all three Dark Guardian finish variants correctly assigned to the same file, no overwrite), but reported "i didnt get a warning" — the "Also used for" note never appeared while he was actually doing it. Static review of the full data/render pipeline (`getProductVariantsWithSuggestionsHandler` → `usedByOptionValues` → `showFilePickerForVariant`'s template) didn't turn up a definitive bug; the wiring looked correct on paper. Rather than keep chasing an unreproducible timing issue, made the indicator **persistent** instead of relying on a one-time note inside the picker modal: `populateVariantAssignments()`'s already-assigned row now shows its own "Also used for: X, Y" note directly under the filename (using the same `usedByOptionValues` data, filtered to exclude the row's own option value), so the multi-finish case stays visible on the variant list itself, not just for the moment the picker happens to be open. `styles.css` gained a small `.assigned-file-info`/`.also-used-note` wrapper for it.

**Separate, related question James raised, not yet actioned: renaming an existing variant's label, or adding a brand-new one** (his example: rename "Bronze & Silver" to "Antique Silver" and add a new "Antique Bronze" variant). Checked the current `renderShopifyVariantsTable()` (the plain Variants table) and confirmed: the Variant/option-value column is rendered as plain text, not an editable field — Printventory's product editor has **no UI today for renaming or adding a variant**, only for editing an existing variant's SKU/price/stock. This also intersects directly with GR-OPS-002's standing rule ("Never rename a Shopify option value by CSV import... rename in the Shopify admin") — that rule is written against the CSV-import path specifically (CSV matches existing rows on Option1 Value, so a changed value there deletes and recreates the variant, breaking the Etsy/QuickSync link), which is a different mechanism from Printventory's direct Shopify Admin API calls. A rename done via Shopify's own `productOptionUpdate` mutation (by variant ID, not by matching on the old label) wouldn't have that CSV-specific failure mode and wouldn't touch the variant's SKU — so it's a legitimate, safer feature to consider adding here, but it's a genuinely new capability (new mutations, new editor UI, and probably its own confirmation/approval step given SKU/pricing records are a controlled authority above this build per the project's own authority order), not a quick fix, and hasn't been scoped or built. **For now, per the existing standing rule, rename/add variants directly in the Shopify admin** — the new variant will show up in Printventory's product editor on the next refresh, same as any other, ready to have a file (new or shared) assigned to it in the variant picker.

**Round 6 — James acted on this and it surfaced a real staleness bug, fixed in commit `6886c3f`.** He renamed "Bronze & Silver" to "Antique Silver" and added a new "Antique Bronze" variant directly in the Shopify admin, per the standing-rule recommendation above. Screenshots showed the result was inconsistent between the two UIs in the same dialog: the plain Variants table correctly showed "Antique Silver" and the new "Antique Bronze" row (with an empty File column, nothing assigned yet, as expected for a brand-new variant) — but the Variant Assignments dialog above it still showed the old "Bronze & Silver" label throughout (including in its own "Also used for" notes), and had no row at all for "Antique Bronze." Root cause: the plain table renders straight from `fetchLiveShopifyData()`'s live Shopify response every time, but the Variant Assignments dialog reads a separate local mirror table (`shopify_variants`) that was only ever populated once, at initial product-linking time — nothing refreshed it on subsequent opens, so a rename or a newly added variant done afterward in the Shopify admin had no way to reach it short of running the separate manual backfill tool. Fixed by re-syncing `shopify_variants` from the same live fetch on every refresh (same delete+reinsert pattern the initial-link code already used) — see "Order-line staleness" pattern above for the general shape of this class of bug (a local mirror table not kept in step with a live or locally-made change).

**Round 6 — Unlink action added, commit `6886c3f`.** James, separately: "I should be able to unlink files completely as well as replace." The Variant Assignments dialog's assigned-variant row only offered Replace (immediately opens the file picker for a different file) and Open — no way to remove a confirmed assignment outright and return the variant to its unassigned/suggested state. Added an `unassignFileVariantHandler` (deletes the `shopify_variant_file_links` row for that variant, mirrors `assignFileVariantHandler`'s order-line re-match/live-refresh so any order line auto-matched via this assignment falls back correctly) and a new "Unlink" button next to Replace/Open, styled distinctly (reddish) as a destructive action and confirmed before it runs.

**Round 6 — Etsy tag count/limit indicator added, commit `6886c3f`.** James: "I think tags should have a count as well. Etsy has a max and we should adhere to this," later clarifying he wanted a "10/14 or whatever the number is" style display. Confirmed against Etsy's own help documentation (not assumed): **13 tags maximum per listing, 20 characters each**. Added a live "N/13 tags" indicator next to both Tags fields (the linked-product form and the new-product form), parsing the comma-separated value the same way the push payload itself does; turns red with a specific reason in its tooltip (too many tags, or which individual tag(s) exceed 20 characters) when either Etsy limit would be breached. This is advisory only — Shopify itself has no tag-count limit, and Printventory doesn't currently confirm whether QuickSync actually carries tags through to the paired Etsy listing, so the indicator is there to keep the listing itself within Etsy's own limits in case it's ever needed there, not a claim about what QuickSync does.

### Visible feedback for "Push to Shopify" — 2026-10-05

**Follow-on, round 5 — the visible-feedback fix immediately caught a real, previously-silent bug.** With the badge now visible, James's next push surfaced a genuine red "Push failed" error he'd never have seen before: `Error invoking remote method 'delete-shopify-product-media': Error: mediaIds: Media ids gid://shopify/MediaImage/76818190467398,gid://shopify/MediaImage/76818190500166 do not exist`. Root cause, confirmed in `shopify.js`: `deleteProductMedia()`'s `productDeleteMedia` call treated **any** `mediaUserErrors` entry as a hard failure — including "this media is already gone," which is the exact end state a delete was trying to reach in the first place. Most likely trigger: a stale local photo-diff baseline, where a prior push's delete step succeeded but a *later* step in that same push failed, so the overall push reported failure and never reached `refreshLiveShopifyData()` to reset the baseline — the next push then retried deleting media that was already deleted. Fixed (commit `c8d866a`): `mediaUserErrors` entries matching "do not exist" are now filtered out and logged as a warning rather than thrown; any other, genuinely different error (permissions, deleting a product's last image, etc.) still throws exactly as before. `deletedIds` also now falls back to the full requested id list when Shopify's own `deletedMediaIds` comes back empty (everything requested was already gone, so nothing needed deleting this call), so the caller still sees its target state achieved.

### Order-line staleness after a local variant-file assignment — 2026-10-05, round 5

James, same round: "also, now they are all linked, the products page didnt refresh and change the button" — after confirming all three Dark Guardian finish variants' file assignments in the product editor, the corresponding Orders-pane line(s) for those same products kept showing "Open Product Manager" instead of updating to "Open in Slicer." Root cause: `shopify_order_line_items.link_status`/`matched_model_id` are only ever recomputed by `matchOrderLineItem()` during a full `syncShopifyOrdersHandler` run — confirming a variant's file assignment locally (via `assignFileVariantHandler`) never touched already-synced order lines at all, so only the *next remote Shopify sync* would have picked up the change.

Fixed (commit `c8d866a`): `assignFileVariantHandler` now, immediately after writing the assignment, looks up any `shopify_order_line_items` rows for that same `shopify_variant_gid` (skipping any already `manually-linked`, same protection as a real sync), re-runs `matchOrderLineItem()` against each, writes the updated `matched_model_id`/`matched_shopify_product_id`/`link_status` in place, and — mirroring `syncShopifyOrdersHandler`'s own pattern exactly — emits a `shopify-orders-synced` event to the renderer so the Orders pane's badge and buttons refresh live, with no full remote sync required. Wrapped in its own try/catch so a problem re-matching order lines can never break the variant assignment itself.

### Manual-link search: custom Fuse.js combobox with a plain-substring fallback — 2026-10-05

The unmatched-line reconciliation input originally used a native `<input list="...">` bound to a `<datalist>` of all model names. James's second round of testing (screenshot, order #1038 "Replacement Postage") found two real problems: the browser's own suggestion popup doesn't scroll reliably once the model list runs into the thousands, and matching felt prefix-only rather than "recognize characters" (substring/fuzzy) search.

Fixed in commit `df4e420` by replacing the datalist entirely with a small custom combobox in `orders-pane.js`/`styles.css`: a plain text input plus Printventory's own scrollable results panel (`max-height: 200px; overflow-y: auto`), filtered on every keystroke with Fuse.js, arrow-key navigation, Escape/focus-out to close, and `mousedown` (fires before the input's blur) rather than `click` for selection.

**Third-round report:** typing into the box worked (the input itself is a plain native text field), but the dropdown seemed to never open or filter as James typed. No bug was found in the DOM structure, CSS, or event-delegation wiring on static review. Fixed defensively (commit `8783c8a`) rather than chase an unconfirmed root cause: `ensureModelsFuse()` now verifies `window.Fuse` is actually a constructor before using it and falls back to a plain case-insensitive substring filter otherwise; `handleComboboxInput()` wraps the search in try/catch and shows a visible "Search failed - see console" message in the dropdown on error instead of doing nothing silently.
